## 2. Pilot migration: category form

- [x] 2.1 Migrate `src/app/(app)/settings/category-form-dialog.tsx` from `useActionState` to `useAppForm`, using the existing category Zod schema from `src/lib/validation/category.ts` as the client validator.
- [x] 2.2 Manually verify: field-level errors appear on blur/change before submit, server-side errors (e.g. duplicate name) still surface, and the category Server Action is unchanged. (Verified via browser: blur-on-empty shows an error, typing a valid value clears it immediately, and create/edit round trips succeed with no console errors. Category create/update has no server-only uniqueness check today, so the "duplicate name" case doesn't apply here — the `{error, fieldErrors}` → `onSubmitAsync` mapping is otherwise generic and will be exercised by auth's duplicate-email case in section 3.)
- [x] 2.3 Adjust `use-app-form.ts` / the `Field` wiring based on anything learned from this pilot before continuing. (Found and fixed a real bug: a field blurred without ever being typed into never validated, since `onChange` never fires without a change event. Fixed by adding a `handleFieldBlur` helper that marks the field touched *and* forces the `onChange` validator to run via `field.validate("change")` — reusing the same error slot so a later real edit clears it immediately. An initial attempt using a separate `onBlur` validator left a stale error after typing a valid value; `revalidateLogic`/`onDynamic` was also tried and rejected because its blur/change mode split only revalidates on change after a submit attempt, not pre-submit. Every subsequent form's fields must call `handleFieldBlur(field)` on blur, not `field.handleBlur` directly.)
