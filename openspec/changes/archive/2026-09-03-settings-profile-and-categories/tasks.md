- [x] 1.1 Add `updateProfileSchema` (`registerSchema.pick({ name, email }).partial()`) and a `changePasswordSchema` (`currentPassword: z.string().min(1)`, `newPassword: registerSchema.shape.password`) to `src/lib/validation/auth.ts`.
- [x] 1.2 Add `AuthService.updateProfile(userId, input)`: check email uniqueness against other users (`findUnique` by email, reject if match has a different `id`), update the `User` record, return `PublicUser`.

- [x] 1.6 Add `tests/auth-service.test.ts` covering: successful profile update, email-collision rejection, successful password change, wrong-current-password rejection.

## 2. Categories: Update & Delete

- [x] 2.1 Add `updateCategorySchema` to `src/lib/validation/category.ts` (name/icon/parentCategoryId, all optional, same shape as `createCategorySchema` minus `type`).
- [x] 2.2 Add `CategoryService.update(userId, categoryId, input)` to `src/lib/services/category-service.ts`: `getOwnedCategoryOrThrow`, reject if `input.parentCategoryId === categoryId`, validate a provided `parentCategoryId` with `getOwnedCategoryOrThrow`, then update.
- [x] 2.3 Add `CategoryService.getUsageCount(userId, categoryId)`: `getOwnedCategoryOrThrow`, then `prisma.transaction.count({ where: { categoryId } })` — backs the Settings delete-confirmation copy (design.md D2).
- [x] 2.4 Add `CategoryService.delete(userId, categoryId)`: `getOwnedCategoryOrThrow`, then check `prisma.transaction.count({ where: { categoryId } })` — if `> 0`, throw `AppError("CONFLICT", ...)` naming the count instead of deleting (see design.md D1: a DB CHECK constraint makes deleting an in-use category impossible outright, discovered during 2.6). Otherwise `prisma.category.delete`, relying on the existing `onDelete: SetNull` cascade for `Category.parentCategoryId` (children orphan to top-level; no manual cleanup needed there).
- [x] 2.5 Add `src/app/api/categories/[categoryId]/route.ts` with `PATCH` (update) and `DELETE` handlers, following the `requireAuth()` → parse → service-call → `toErrorResponse` pattern in `src/app/api/categories/route.ts`. Add a `GET` on the same route returning the category plus its usage count (task 2.3) for the delete-confirmation dialog.
- [x] 2.6 Added tests in `tests/category-service.test.ts` covering: rename, re-parent, self-parent rejection, delete with no references, **delete with referencing transactions rejected** (revised from the original "becomes Uncategorized" expectation — see task 2.7/design.md D1), delete succeeds after transactions are reassigned to a different category, delete with child categories (verify children's `parentCategoryId` becomes `null`), cross-user access rejection on both update and delete.
- [x] 2.7 *(discovered during 2.6, superseded during 2.6)* Initially "fixed" a suspected `AnalyticsService.getCategoryBreakdown` gap (excluding orphaned-category transactions instead of bucketing them "Uncategorized"). That fix was reverted once the real blocker was found: `transactions_type_shape_check` (a DB CHECK constraint from `core-financial-architecture`) makes orphaning an in-use category's `categoryId` impossible outright — `CategoryService.delete` now blocks deletion while `usageCount > 0` instead (see task 2.4 and design.md Context/D1). `getCategoryBreakdown` is back to its original, unmodified form. See design.md Context for the full discovery sequence.
